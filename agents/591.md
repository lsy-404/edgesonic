# Karaoke mode and integrated media playback

## Requirements
- Move the entry into Tools and label it K歌模式 / Karaoke mode.
- Separate preparation from the fullscreen singing stage. Hide management UI by default on the stage, with an optional QR panel at the upper right and accessible ways to show controls or leave fullscreen.
- Force rooms closed after twelve hours or five minutes without the controller.
- Reuse the independent player and existing application infrastructure; do not require a separately deployed media service.
- Support platform account authorization for playback entitled to the account, including available higher quality and membership content. Do not claim that ordinary OAuth grants media playback rights or that every restriction can be removed.
- Preserve independent audio/video catalog objects, many-to-many links and watch/listen position continuity.

## Implementation boundaries
- Reuse the clean task worktree at origin/main (8eb20213); the primary checkout's unrelated work remains preserved on its existing recovery branch.
- The primary agent owns lifecycle, media/account architecture, audit, integration and verification. Delegate the independent fullscreen/preparation UI in a fresh worktree.
- No new automated tests are requested. Run existing contract checks and real local playback/UI checks.
- A new integrated Cloudflare Container is authorized. Without it, compatibility mode uses library media, with an optional external iframe switch. Both standalone video and library audio plus muted iframe are allowed. Switching unloads the iframe; quality, login and synchronization limits must be explicit.
- Mobile requests support library/platform search where available, URLs, short links and BV/AV references.
- Platform authorization is per host account and encrypted at rest with AES-GCM and purpose-separated key derivation from a private persisted MediaContainer key. Encryption is performed through private Durable Object RPC and survives normal Worker upgrades. Guests never receive credentials. Bilibili uses explicit QR confirmation; YouTube uses an explicitly imported cookie file because yt-dlp OAuth is unsupported.

## Verified upstream constraints
- yt-dlp's maintained YouTube extractor documentation states that OAuth login no longer works and account cookies are used instead.
- The existing Worker already accesses its Sandbox container through containerFetch; this does not require a new public service endpoint.

## UI refinement
- Stage control uses a seek slider, not jump buttons. Uncontrolled standalone iframes do not show an inoperative timeline.
- The fullscreen QR is a bare image without a card, border, label or surrounding controls, visible by default with opaque modules and a 28%-opacity light background and subtle blur and independently hideable.
- Replace long room/invite URLs in QR payloads with a six-digit numeric room PIN resolved server-side. Encode QR with H error correction and crop exactly to the module bounds without external padding by default, as explicitly requested.

- Final invitation format is `/k?c=114514`; `/k` accepts manual six-digit entry. D1 reserves active PINs without overwriting collisions; every lookup rechecks the live room.

- The stage seek controls sit in a centered floating card capped at 560 px, revealed by pointer interaction and hidden on inactivity; it does not stretch across the viewport.

- User confirmed the cropped QR scans on their device. Keep that default; on pointer hover or keyboard focus, remove blur and restore an opaque white background plus four-module quiet zone. Remove the toolbar help and preparation buttons; remaining actions use existing icon components.

- Final mode boundary: preparation and true browser fullscreen only. Leaving fullscreen (including Escape) returns to preparation. A rejected fullscreen request remains on preparation and reports the failure; no windowed stage fallback.

- Preparation QR is fully opaque and unblurred. Only the default fullscreen QR uses the translucent light modules and subtle blur.

- User restored the existing hash-route convention: final invites use `/#/k?c=114514` and manual entry uses `/#/k`. The temporary history-mode experiment is removed.
- Production browser validation exposed one remaining pathname-query reader in the preparation room-code label. Parse the canonical hash-route query there as well; QR payloads and manual joining already use the correct contract.
- Browser logs confirmed deleted old build chunks broke Clients/Tools/About navigation during preview updates. Use Vite preload-error recovery once per loaded build, preserving the intended hash route; HTML is marked no-cache.
- Final delivery request explicitly authorizes production deployment. Remove the duplicate Work Mode button in the Tools header while preserving the Work Mode card. Deploy from the focused worktree, preserve existing production bindings, secrets and schedules, and include the optional media container already authorized by the user.
- Subsequent UI refinement: Tools contains only a Karaoke entry matching the Work Mode card. Karaoke enablement, default queue policy, media mode and platform accounts live inside an independent settings popup on the authenticated preparation page.
- Audio-only playback reuses NowPlaying's cover, track metadata and synchronized lyrics layout instead of the separate title block and small lyric strip. Video listening supplies its own title metadata without leaking the previous library track's cover or lyrics. Its media element stays mounted while hidden to preserve playback position. Existing stage controls and QR behavior remain.
- User explicitly selected anonymous mobile guests with authenticated hosts. Guest entry becomes a separate `/ktv/` document and invitations use `/ktv/?c=123456`. It must not initialize site login, SSO or activation gates. The main app and authenticated host retain hash routing; platform account authorization remains optional.
